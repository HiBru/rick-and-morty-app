### Gradle wiring that is easy to get silently wrong

- **`gradle.properties`** needs three lines the scaffold lacks: `ksp.useKSP2=true`, `room.useKSP2=true`, `ksp.allow.all.target.configuration=true`. (KSP ≥ 2.3.0 may no longer need the first two, but they are part of the proven configuration and are harmless if redundant.)
- **Room's processor is wired per target.** `ksp(...)` is deprecated for KMP, and `kspAndroidMain` is *silently ignored* — Room generates nothing and the build still succeeds:
  ```kotlin
  add("kspAndroid", libs.room.compiler)
  add("kspIosArm64", libs.room.compiler)
  add("kspIosSimulatorArm64", libs.room.compiler)
  ```
- **JUnit Platform must be enabled on the task.** The KMP library plugin has no `testOptions` DSL, and `tasks.named("testAndroidHostTest")` fails to resolve at configuration time:
  ```kotlin
  tasks.withType<Test>().configureEach {
      if (name == "testAndroidHostTest") useJUnitPlatform()
  }
  ```
  Without it, JUnit5 tests are **skipped and the build reports success**. Gradle 9.8 also removed auto-injection of test-framework runtime deps, so `junit-platform-launcher` must be `runtimeOnly` or the task fails to start. `kotlin-test-junit5` in `androidHostTest` is what makes `commonTest`'s `kotlin.test` annotations run under JUnit Platform on the JVM side.
- **`useJUnitPlatform()` regressing is a loud failure, not a silent skip** — *measured in Task 16 by removing it*. The build fails during dependency resolution: `kotlin-test-junit5` is rejected, because Gradle selects test-framework variants by capability, and zero result files are produced. The guard test that existed for this (`ToolchainJvmTest`) was therefore retired in Task 16 — `CharacterListViewModelTest` and `KoinGraphTest` are both directly Jupiter-annotated anyway, and `@RegisterExtension` is a stronger canary than `@BeforeEach` was: without the Jupiter engine, `Dispatchers.setMain` never runs and every ViewModel test fails outright.
- **The Koin BOM does not reach the test source sets.** `platform(libs.koin.bom)` in `commonMain` constrains `androidMain`'s versionless `koin-android` (verified), but `commonTest` / `androidHostTest` do not extend `commonMainImplementation`. The first versionless Koin artifact added there — `koin-test` is the likely one — needs its own `implementation(project.dependencies.platform(libs.koin.bom))` or it fails with "Could not find io.insert-koin:koin-test".
- **No Compose UI-test artifact is wired yet, and Task 17 now owns adding it.** `CLAUDE.md` describes `ComposeTestRule` and the robot pattern, but nothing declares the dependency. Task 13 turned this from "if a UI test is wanted" into an obligation: the character row's clickable card exposes no accessible name, and a semantics assertion is the only way to verify a fix without guessing — see the Task 13 entry under *Domain decisions*.
- **`:shared:connectedAndroidDeviceTest` has no runner dependency.** `withDeviceTestBuilder` names `AndroidJUnitRunner`, but Task 1 removed the scaffold's `androidx.test` catalog entries as unused. An instrumented test therefore needs `androidx.test:runner` re-added plus an `androidDeviceTest` dependency block — or drop the device-test builder, since no device tests exist.
- **There is no typed `androidHostTest` source-set accessor.** `androidHostTest.dependencies { }` fails to compile the build script; use `getByName("androidHostTest").dependencies { }`. (`androidMain`, `commonMain`, `commonTest` and `iosMain` all do have accessors.)
- **`compose-ui-backhandler`** must be declared explicitly *if* `BackHandler` is ever used: `compose-ui` pulls it in transitively on iOS but not on Android, so such code compiles for iOS and breaks the Android build.
- Set `compose.resources { packageOfResClass = "de.shinz.rickandmortyshowcase.generated.resources" }`. `publicResClass` is unnecessary in a single module.
- Do **not** add `de.mannodermaus.android-junit5` — it drives the old `com.android.library` `testOptions` DSL, which this plugin does not have.

**These four light values are not the first choices — do not "restore" them.** The originals failed WCAG AA and were corrected in Task 2 against measured ratios: `onSurfaceMuted #6B7280` was 4.35:1 on `surfaceVariant`, `statusAlive #16A34A` was 2.96:1, `statusDead #DC2626` was 4.34:1, and `statusUnknown`'s light/dark pair was transposed, leaving a light grey on white at 2.54:1. All 36 foreground/background pairs now pass 4.5:1, worst case 4.51:1. The status colours tint a label as well as a dot, so the bar is 4.5:1, not the 3:1 a non-text graphic would get.

- `AppSpacing` — scale steps `xs 4`, `sm 8`, `md 12`, `lg 16`, `xl 24` on a 4dp rhythm, plus the named `screenPadding 20`. `screenPadding` is a named token, not a sixth step, so the 5–6 step ceiling in `CLAUDE.md` is not yet reached
- `AppRadius` — `sm 8`, `md 12`, `lg 16`, `full 999`
- `AppSize` — `icon 24`, `iconSmall 18`, `avatar 64`, `statusDot 8`, `touchTarget 48`, `detailImage 220`
- `AppBorder` — `hairline 1`
- `AppTypography` — `displayTitle 28`, `screenTitle 22`, `cardTitle 17`, `body 15`, `caption 13`

**Only `colors` varies by theme**; the other five are hoisted to top-level `val`s. Typography is hoisted too because the app uses the system font — the reference project remembers its typography inside composition only because Compose Resources' `Font()` is `@Composable`, which does not apply here.

The same five styles are also mapped onto the Material 3 slots as `appMaterialTypography` and handed to `MaterialTheme(typography = …)`. Material components read `MaterialTheme.typography`, never `AppTheme.typography`, so without the mapping a dialog renders at stock M3 sizes and does not match the screen behind it.

**An unmapped slot is not a graceful fallback — it is stock Material purple or a stock size.** Finding them means checking which token each component actually reads, not assuming. The three that bit in Task 2: `secondaryContainer`/`onSecondaryContainer` is the `NavigationBar` selected pill (on screen for all three tabs), `surfaceContainerHigh` is every `AlertDialog` background (three screens per `SPEC.md`), and `headlineSmall` — not `headlineMedium` — is the `AlertDialog` **title**. Equally, do not override a slot that already fits: `labelLarge` mapped to `cardTitle` made every dialog button 21% larger than M3 intends, so the label slots are left stock.

> **Name trap:** `border` is both a *color* (`AppTheme.colors.border`) and a *group* (`AppTheme.border.hairline`). Same class of trap as `size` shadowing `DrawScope.size` — read the line twice before assuming which one a call site wants.

> **Silent failure to watch for:** every `staticCompositionLocalOf` has a default, so a token group dropped from `AppTheme`'s `CompositionLocalProvider` still compiles and still renders. For the five dimension groups the default *is* the value, so nothing breaks — but `LocalAppColors` defaults to `appLightColors`, which means a missing `provides` would leave dark mode silently light. No Compose test artifact is wired to catch this, so **Task 10's launch check must look at dark mode on both platforms**, not just that the app starts.

### Domain decisions made in Task 3 — do not "correct" these

- **`DataError` is deliberately shorter than the canonical list in `android-error-handling`.** `Network` has 7 constants and `Local` has 2. There is no `UNAUTHORIZED`, `FORBIDDEN`, `CONFLICT`, `BAD_REQUEST` or `PAYLOAD_TOO_LARGE` because the API is public and read-only — the app never authenticates and never uploads. Every constant costs a branch *and* a user-facing string in `toUiText()`, so an unreachable one is a string explaining a login the user does not have. Anything unexpected is `Network.UNKNOWN`.
- **`Local` has no `NOT_FOUND`.** A character that is not favourited is the normal case, so `getFavorite` returns `Result<Character?, DataError.Local>` and reserves `Result.Error` for things that actually went wrong. That is what lets the detail screen read a miss as "fetch from the API" rather than as an error to display. Deleting an absent row is a no-op for the same reason.
- **`Character` carries `originUrl`, `locationUrl`, `episodeUrls` and `url` even though no screen shows them.** `SPEC.md` requires favouriting to persist the whole API record for offline rendering, and the database is only reachable through this model. The detail screen's episode count is `episodeUrls.size`.
- **Only `status` is an enum.** It is the one character field that drives a colour as well as a label. `species`, `type` and `gender` stay `String`: their values are unbounded (Human, Alien, Poopybutthole, …) and are displayed as the API words them.
- **`observeThemeMode()` returns `Flow<ThemeMode>`, not `Flow<Result<…>>`.** A theme preference has a sane default, so a failed read falls back to `SYSTEM` rather than becoming something the user has to see. The *write* does report failure.
- **The two favourites `observe…` functions also have no error channel**, for the same reason: `SPEC.md` gives the Favorites screen an empty state but no error state. A read failure degrades to "no favourites". **This obliges Task 7 to absorb failure with `catch` inside the implementation** — otherwise a Room error or a malformed episode-url column reaches the collector as a raw exception, which `CLAUDE.md` forbids outright.
- **The shell is two nested hosts, and that is load-bearing** (Task 12). Outer host: `DashboardRoute` + `CharacterDetailRoute`. Inner host inside the dashboard's `Scaffold`: the three tabs. Detail hides the bottom bar **by construction**, not by a `showBottomBar` toggle. *A first attempt flattened all four into one host and toggled the bar — `currentBackStackEntryAsState` emits when a transition **starts**, so the bar would appear or vanish while the outgoing screen is still animating (700ms fade on Android, 500ms slide on iOS), relayouting it mid-transition.* `CLAUDE.md` described the nested shape all along; the flat version was an undocumented deviation.
- **The tab host fades; the outer host keeps the platform transition** (Task 12). Navigation-compose's iOS default is a horizontal push with predictive-back — correct for detail, wrong for tabs, where it makes switching look like opening a screen and lets a right-swipe drag a tab away. The inner host therefore sets `fadeIn`/`fadeOut` explicitly.
- **Detail is outside the `Scaffold`, so it takes window insets itself** (Task 12). Caught on device: after the restructure the detail title ran under the status bar, because only the dashboard's children receive `innerPadding`. It uses `WindowInsets.safeDrawing.asPaddingValues()`.
- **`contentWindowInsets = WindowInsets.safeDrawing`**, not the `Scaffold` default of `systemBars` — the default ignores `displayCutout`, which puts content under the notch in landscape.
- **`NavDestination.hierarchy` already exists** in navigation-common; do not hand-roll `generateSequence(this) { it.parent }`. It is also pointless for a flat tab host, where the only parent is the unnamed root graph and can never match a route.
- **The shell consumes insets once, for every screen** (Task 12). `Scaffold`'s `innerPadding` is **passed into each `composable<…>` body** rather than applied to the `NavHost` by an ancestor — a screen cannot un-pad its parent, and SPEC's scrolling lists want to route it into `LazyColumn(contentPadding = …)` so content scrolls under the bars. Verified on device: the screen title no longer collides with the clock.
- **Tab state preservation is `saveState` + `restoreState` + `launchSingleTop`, together** (Task 12). All three, plus `popUpTo(graph.findStartDestination().id)`, or the back stack grows one entry per tab switch. Verified by scrolling Home, switching to Settings, returning, and hashing the rendered content: byte-identical.
- **The selected tab comes from the back stack** (Task 12), never from a `UiState` — the shell has no ViewModel and no assembler. `AppBottomBar` itself takes an already-resolved `TopLevelDestination`, not a `NavDestination`, so it is a plain stateless component that previews without a `NavController` and a built graph. The resolution defaults to `HOME` while the back-stack entry is still `null`, or the bar renders with nothing selected for one frame.
- **A page `404` means end-of-list — but only after page 1** (Task 14). The API serves a page past the last one with `404` rather than an empty list, so `GetCharacterPageUseCase` is not a pass-through: it collapses `NOT_FOUND` into `CharacterPage(emptyList(), hasMore = false)`. Left alone it would surface as `error_not_found` — "We couldn't find what you were looking for" — which is wrong twice at the bottom of a list: the user scrolled rather than searched, and **retry cannot fix it**. *Page 1 is excluded deliberately*: a `404` there is the API being broken or moved, not "no characters exist", and collapsing it would paint a blank screen with no error and no retry. Only `NOT_FOUND` collapses; every other failure stays a failure on every page, or going offline mid-scroll would silently end the list.
- **The list's paging state is one sealed field, not a flag beside a nullable error** (Task 14). The plan originally sketched `isLoadingNextPage` + `initialLoadError` on the `ViewModelState`; the implementation holds `pageLoad: CharacterListPageLoad` — `Loading` / `Idle` / `Failed(error)`. Two reasons, both found in review. A boolean beside a nullable error is **a free 2×2 whose fourth corner is nonsense**: in flight *and* failed would tell the screen to draw a spinner and an error row at once, the invariant would live only in a comment, and a retry that set the flag without clearing the error would compile. And the first/later split is not state at all — it is `characters.isEmpty()`, which is sound because that list only ever grows, so **the assembler** derives `isInitialLoading`/`isNextPageLoading` and `initialLoadError`/`nextPageError` from one field plus the buffer. Same argument the single-error-field decision already accepted, carried one step further.
- **`pageLoad` defaults to `Loading`, and that default is what the first frame paints** (Tasks 14-16). `stateIn`'s initial value is `assemble(EMPTY, CharacterListViewModelState())`, and it is what composition reads until the first real emission. The default encodes the truth: there is no reachable state with no characters, no error and nothing in flight, because the ViewModel requests page 1 from `init`. *An earlier revision justified it by claiming `combine` could not emit until the Room flow answered; Task 16 made that moot by giving the favourites arm its own `stateIn` with an `emptySet()` initial value. The default is still right, for the simpler reason.* **Consequence for Task 17's previews:** a "loaded, idle" preview must pass `pageLoad = Idle` explicitly.
- **The end-of-list guard has three conditions, and the third is the one that gets forgotten** (Task 14). `OnEndOfListReached` fires on every scroll callback, not once per page, so the ViewModel guards on *`pageLoad is Idle` and `!endReached`*. `Idle` rules out a second request while one is in flight **and** a request after a failure — without the latter, a user parked at the bottom of a failed list re-fires it on every scroll frame, which offline is an unbounded retry loop and makes `SPEC.md`'s retry affordance decoration.
- **An empty page 1 that *succeeded* is a failure, and the use case is where that is decided** (Tasks 14-15). Left as a success it paints a blank screen with nothing to scroll, so paging is never re-triggered and the user cannot get out. `GetCharacterPageUseCase` therefore returns `SERVER_ERROR` for it — an API that answers an out-of-range page with `404` has no reason to serve `200` with no characters. The check is **first-page-only**, like the `404` rule it mirrors: a later page legitimately comes back empty, since that is what the `404` collapse produces, and checking every page would mean paging could never stop.
  *Task 15 first solved this in the assembler, synthesising a `DataError.Network.UNKNOWN` so the user would at least get a retry button. Two things were wrong with it. The fabricated error was indistinguishable downstream from a real one — no log, no crash report, no future "report this" affordance could tell them apart — and an assembler structurally cannot know whether a request failed. Worse, **the retry could not have worked**: a page that succeeds advances `nextPage`, so retrying from that state would have asked for page 2 and shown characters 21-40 as the start of the list. A failed page is never consumed, so moving the decision upstream makes retry ask for page 1 again.* The lesson generalises: **an assembler projects its inputs and never invents one.**
- **The assembler places errors with the same condition that places indicators** (Task 15). One mapped `UiText`, two slots, `takeIf(isListEmpty)` / `takeIf(!isListEmpty)` — so the full-screen and inline treatments cannot disagree about which half of the screen the user is looking at, and the pair is exclusive by construction rather than by convention.
- **Reusable test fixtures live beside the type they build** (Task 15). `testCharacter(...)` in `commonTest/core/domain/model/` replaced four hand-written copies of `Character`'s fourteen-field constructor, and `UiText.resolve()` in `iosTest/core/ui/` backs all three string tests. Deliberately **not** `CharacterPreviewSamples`, which lives in `commonMain` for the previews: a test asserting against preview data breaks when a preview is retuned.
- **`CharacterListUiState` is `@Immutable` for the same reason `UiText` is** (Task 14) — it holds a `List<CharacterUi>`, which is unstable to the compiler. Verified the same way: `$stable` is the compile-time constant 0. The compose skill names `@Stable` here; `@Immutable` is the stronger and equally true claim, since the assembler builds a fresh state each time and nothing mutates one. `CharacterListViewModelState` and `CharacterListData` are left unstable on purpose — neither is ever a composable parameter.
- **`ShowSnackbar` needs a host that does not exist yet** (Task 14). The list's `UiEvent` carries it for a failed favourite *write*: the heart is driven by the favourites flow, so a failed write just leaves it where it was and the user watches nothing happen. The dashboard `Scaffold` in `navigation/` has no `snackbarHost` — **Task 17 must add one** and decide whether it belongs to the screen or the shell (Tasks 19 and 20 need the same thing).
- **One channel carries both event kinds, and only one of them wants to be retained** (Task 16). `Channel(BUFFERED)` + `send` is right for `ShowSnackbar`: `ObserveAsEvents` stops collecting below `STARTED`, so a message raised while detail covers the list queues and fires on return, where `trySend` would drop it. The same retention is **wrong for `NavigateToDetail`** — a double-tapped row sends two, and the one not consumed before the screen drops below `STARTED` fires on return and re-opens detail. **Task 17 owns the fix**, at the collection site: the ViewModel cannot know whether a navigation already happened.
- **ViewModels are deliberately not resolved in `KoinGraphTest`** (Task 16), although a `viewModelOf` arity mistake is exactly the runtime failure that file exists to catch. Resolving one *constructs* it, and `CharacterListViewModel` requests page 1 from `init` — so the graph test fires a real HTTP request and leaves a live `viewModelScope` running past `Dispatchers.resetMain()`. *Measured: its uncaught exception failed an unrelated use-case test in a different package, reported as "uncaught exceptions before the test started".* Stubbing the engine would hide it but also stop the test proving the real engine binding resolves. What makes the omission acceptable: `viewModelOf(::X)` resolves each constructor parameter **by type**, and every one of those types is resolved individually in the same test.
- **A fake that never suspends makes an in-flight state untestable** (Task 16). The data-source fakes answer instantly, so on an `UnconfinedTestDispatcher` a page request completes inside `onAction` and `pageLoad == Loading` is never observable — which left the `Loading` half of the end-of-list guard passing every test while being deletable. A `@Nested` class with a paused `StandardTestDispatcher` is where anything mid-flight gets pinned; `@RegisterExtension` is a per-class field, so the dispatcher genuinely is the fixture. Verified by mutation: dropping the `Loading` check fails exactly that one test and nothing else.
- **Each screen owns its own snackbar host** (Task 17), not the dashboard shell. The detail screen sits outside the shell's `Scaffold` and would need one regardless, so a shell-level host would mean two mechanisms for one job — and the shell would have to pass a `SnackbarHostState` down into feature screens it otherwise knows nothing about. Every screen already receives the window insets needed to place it above the bottom bar. `AppSnackbarHost` paints its own `Snackbar`, because that shape comes from a Material token rather than `MaterialTheme.shapes`.
- **A `UiText` cannot be shown from an event handler** (Task 17). Resolving one is `@Composable`; `ObserveAsEvents`'s callback is not. So the event parks the `UiText` in state, composition resolves it, and a `LaunchedEffect` shows it. A side benefit: a message raised while the screen was covered resolves in the *current* locale rather than the one at emission.
- **Navigating once per tap is a destination check, and it costs a transition-long dead zone** (Task 17), in `AppNavHost` because the Root has no view of the back stack. A row double-tapped in one frame sends two events, and `ObserveAsEvents` collects on `Main.immediate`, so both are handled before the frame ends; `navigate` updates the back stack synchronously, so by the second one the current destination is already detail. Verified: double-tap, one back press, Home.
  **The cost, measured:** `currentBackStackEntry` stays on detail until a *pop* completes too, so for the length of the back transition (700ms on Android) a tap on another row is silently swallowed — ripple, nothing else. Confirmed on device both ways: tapping immediately after back does nothing, tapping 2s after back opens detail. *An earlier revision also required `isAtLeast(RESUMED)`, to catch a navigation event that had queued behind the detail screen. That was dropped — it widened the same dead zone for a case that is much narrower than it looks, since a second tap needs a visible, interactive Home.* **The dead zone is inherent to deduping on back-stack state**, not to either specific check: a replay-free `MutableSharedFlow` for navigation would fix the deferred duplicate but not this, because the same-frame double tap still needs the destination check. Ignoring input mid-transition is the accepted trade; stacking two detail screens is not.
- **The detail screen's three top-level states are exclusive by construction** (Task 18). The assembler keys `character` on `load is Idle` rather than on "no error", so loading, error and content cannot overlap — a character beside an error would show stale content under a message saying it failed, and one beside a spinner would put the spinner over it. Two of those pairings are unreachable from the ViewModel today; they are pinned anyway, because an assembler is a pure function of its inputs and the screen is written against the contract, not against what the ViewModel happens to produce.
- **The confirm-before-remove rule is enforced in the ViewModel, not only by the dialog** (Task 18). `OnConfirmRemoveFavorite` returns unless a removal is actually pending: a confirm button tapped twice before recomposition closes the dialog, or a stray action, must not delete. `SPEC.md` makes confirmation unconditional, and the ViewModel is the last layer that can hold that line. Likewise `OnFavoriteClick` resolves the character **before** branching — opening the dialog without one would leave a pending removal with no dialog to dismiss it, which then springs open the moment the character arrives. Both are mutation-verified.
- **"Added to the API" is the label for `created`** (Task 18). It is the API record's creation date, not an in-universe one — a bare "Created" is the reading that actually misleads. It does put the word "API" in front of the user; worth revisiting in Task 22.
- **"The database has not answered" is not "there are no favourites"** (Task 20). `FavoritesData.characters` is a `List<Character>?`, `null` meaning the flow has not emitted. `combine` cannot emit until it has, so `stateIn`'s initial value is what the screen paints first — with an empty list as the placeholder, a user with twenty favourites is told "No favorites yet" for the length of a Room query. Pinned with a paused-dispatcher test, and mutation-verified: seeding `EMPTY` with an empty list fails exactly that test and nothing else.
  *The review argued for a sealed `FavoritesLoad` instead, mirroring `CharacterListPageLoad` and `CharacterDetailLoad`, on the grounds that a presentation sentinel sits oddly in a `domain/model` type the domain can never produce.* **Kept as the nullable**, for two reasons worth not re-litigating: `<Screen>Data` is a screen aggregate rather than a domain entity — it exists for presentation already — and the two sibling types track a *request the screen made*, which is a different fact from "the flow has not emitted yet". The objection is real but the cure is three types for one bit.
- **Favorites holds no load state of its own, and no `init`** (Task 20). Nothing is fetched, so there is nothing to retry: the database is observed and `SPEC.md` forbids this screen from touching the API. Its ViewModel's graph contains no remote data source at all, which is a stronger guarantee than a test asserting the network was not called. It also takes no `AddFavoriteUseCase` — every row here is already a favourite, so the heart has exactly one meaning and always confirms.
- **`PaddingValues.plus` is shared by both lists** (Task 20), in `core/designsystem`. It was written privately for Home in Task 17 and reimplemented token for token for Favorites, which is the second consumer the promotion rule names — and a landscape or cutout fix to one would otherwise have missed the other. Non-composable, taking `LayoutDirection`, so it is unit-testable. The detail screen deliberately does **not** use it: it applies the horizontal and bottom insets but not the top, because its hero image is meant to run under the status bar.
- **A no-op write cannot be told from a skipped one by looking at the data** (Task 20). `confirming twice removes once` passed whether or not the second confirm reached the database, because removing an absent id is a documented no-op — so the fake now counts deletes. Worth remembering for any "exactly once" assertion against a forgiving data source.
- **A screen's label/value pairs need merging; a clickable row does not** (Task 19). The detail screen's six fields were twelve separate semantics nodes — a screen reader stopped on "Gender" and on "Male" with nothing tying them together. `Modifier.semantics(mergeDescendants = true)` on each field fixes it. **This is the mirror of the Task 13 lesson, not a contradiction**: a list row merges for free because `Modifier.clickable` sets `MergeDescendants` itself, and `AppCard` without an `onClick` adds no clickable and so no merge. The difference is worth knowing before guessing either way — both readings were settled by dumping the tree in a Compose UI test.
- **A subjectless `when` gets no exhaustiveness check** (Task 19). The detail screen branches on `isLoading` / `error != null` / `character != null`, and the fourth corner — which `CharacterDetailUiState()`'s own defaults produce — painted a blank screen with a floating back button. Unreachable from the ViewModel, but invisible to the compiler, and the screen is deliberately written against the state *contract* rather than against what the ViewModel happens to emit. There is now an explicit `else`.
- **Window insets are not just the top and bottom** (Task 19). The detail content column applied the screen gutter horizontally and only the window's *bottom* inset, so in landscape a display cutout or a side navigation bar would have overlapped the name, fields and favourite button — while the back button, which takes the full insets, moved clear of it. Device verification was portrait-only and could not have caught it. The top inset stays deliberately unapplied: the hero image is meant to run under the status bar.
- **The robot pattern is in, on both screens** (Task 19). `CLAUDE.md` sets the threshold at three UI tests on one screen; detail reached five and Home three, each repeating the same nine-line `setContent`. The robots take a `ComposeUiTest` rather than the skill's `ComposeContentTestRule`, because these run through `runComposeUiTest` — there is no JUnit rule on the multiplatform side.
- **No screen preview has a removal-dialog variant** (Task 19). `AppConfirmDialog` renders into its own platform window and never appears in a `@Preview`, so such a value is visually identical to "loaded" and wastes a slot. The dialog's look is previewed through `AppConfirmDialogContent`; its wiring is covered by the screens' UI tests.
- **Compose UI tests only run where a simulator exists** (Task 17). `:shared:iosSimulatorArm64Test` is the only task that executes them, so `./gradlew check` on a non-Darwin agent goes green with zero UI coverage — the mirror image of the hazard the test-split table was written to prevent. `iosTest` also feeds `iosArm64Test`, which no per-task command compiles, so a problem on the device target would first surface in Xcode. The dependency is a catalog entry (`libs.compose.uiTest`) rather than the plugin's `compose.uiTest` accessor, which is what carries `@ExperimentalComposeLibrary` — using the coordinate directly removes the build-script opt-in.
- **`AppColors` gained `inverseSurface`/`onInverseSurface`** (Task 17) for the snackbar, rather than reusing `onSurface` as a fill. The values coincide with the existing text/background pair today, which is exactly why they needed their own names: those two are tuned for text contrast *on* a surface, and retuning either would otherwise move the snackbar with them.
- **The shared engine does not starve paging; the API's own rate limit bites first** (Task 17), closing the question Task 13 left open. At human scroll speed images and page requests coexist fine. A 25-fling burst earned a `429`, which surfaced correctly as the inline error with Retry and the loaded rows intact — the behaviour `SPEC.md` asks for, reached by a path worth knowing about.
- **The paging trigger fires on every change of the last visible index**, not once per threshold crossing (Task 17). The ViewModel owns the "already loading / already failed / already finished" guard, so repeating costs nothing — whereas a once-only effect stalls the moment a loaded page leaves the trigger condition still true.
- **`UiText` is `@Immutable`, and that annotation is load-bearing** (Task 13). Two of its three variants hold a `List`, which the Compose compiler cannot prove stable — so **every** type with a `UiText` field was inferred unstable, and under strong skipping an unstable parameter is compared by *instance identity* rather than `equals`. `CharacterUi` is rebuilt by an assembler on each emission and is therefore never the same instance, so every row of a 20-per-page list would have recomposed on every unrelated state change. Measured with the Compose compiler's stability report (`metricsDestination`/`reportsDestination` compiler args, added and removed again): `character: CharacterUi` went from unstable to `$stable = 0`, the compile-time constant for stable. **The annotation is a promise** — nothing may put a mutable value into `StringResourceText.args`. Re-run the stability report rather than guessing if a future `UiState` looks like it should skip and does not.
- **The row's accessibility was never broken — `uiautomator dump` shows the *unmerged* tree** (Tasks 13, resolved in 17). Task 13 recorded a defect: the clickable card appeared to expose empty `text` and empty `content-desc`, so a screen reader would announce nothing. It also recorded that the obvious remedy could not be verified, because the dump did not change when `mergeDescendants` was applied. **Both observations had one cause.** Dumping the real Compose semantics tree in Task 17 shows the card node already carries `Text = '[Rick Sanchez, Alive · Human]'`, `OnClick` and `MergeDescendants = 'true'` — `Modifier.clickable` sets that itself — and the favourite button survives as its own child node with its own `ContentDescription` and `Role = Button`, because `IconButton` is a merging node and merging stops there. No production change was needed, and the `AppCard` edit attempted in Task 13 would have been a no-op.
  Two lessons worth keeping. **`uiautomator` is the wrong instrument for Compose semantics** — it reports the unmerged tree, where Material's own `IconButton` also looks like two unnamed nodes. And refusing to ship an unverified semantics change was right even though the conclusion flipped: the alternative was a guess that could have made the heart unreachable.
- **Compose UI tests are iOS-only, and that is a platform limit** (Task 17). `compose.uiTest` is wired into `iosTest` (typed accessor — `getByName("iosTest")` fails at configuration time — and it needs `@OptIn(ExperimentalComposeLibrary::class)` in the build script). `runComposeUiTest` needs a real Compose host, which on Android means instrumentation on a device; `androidHostTest` is a plain JVM source set. Semantics are platform-independent, so a tree asserted on iOS is the tree Android builds.
- **`core/ui` holds `AppImageLoaderFactory`, and all HTTP configuration stays in `core/data`** (Task 13). Coil's loader is a presentation concern that merely *uses* an engine, so filing it under data would be the first step towards a module that means nothing — but the client it needs is configured by `HttpClientFactory.createForImages` next to the API client's, because the two timeout sets were first written into two files with different values and nothing linking them. The factory takes a `() -> HttpClient` rather than a client: Coil wraps it in a `lazy`, so the image client is never built on a screen with no images.
- **Images get their own client over the shared engine** (Task 13). Sharing the engine shares the connection pool, which is the part worth sharing; sharing the *client* would put `ContentNegotiation`'s `Accept: application/json` on every image request, which a CDN has no reason to honour. The consequence to watch: `rickandmortyapi.com` serves the JSON *and* the portraits, and a shared engine means shared per-host limits (OkHttp caps `maxRequestsPerHost` at 5, Darwin `HTTPMaximumConnectionsPerHost` at 6) — **a fast scroll can queue the next-page request behind image fetches**. Check it during Task 17's paging verification and the Task 22 fast-scroll pass.
- **Coil is wired explicitly even though it would work without it** (Task 13). `coil-network-ktor3` self-registers — `ServiceLoader` on Android, an `@EagerInitialization` hook on iOS — and would then build an `HttpClient()` with **no timeouts at all**, through declarations Coil marks `@InternalCoilApi`. `setSingletonImageLoaderFactory` is called in `App()` *before* the theme gate, because Coil reads its singleton the first time any `AsyncImage` composes and a later call is ignored. Memory and disk caches are left unnamed in the builder deliberately: naming those slots *replaces* Coil's platform-sized defaults.
- **`coreUiModule` is a fifth DI module** (Task 13), alongside `coreDataModule`, `coreDatabaseModule` and `coreDataStoreModule`. Its one binding is a `single`, and **not because a factory would leak anything** — Coil invokes a `SingletonImageLoader.Factory` at most once, so either scope ends with exactly one `ImageLoader`. It is a `single` because this plan reserves `factoryOf` for use cases and assemblers, where a leaked instance would mean leaked *screen* state. It uses `single { }` rather than `singleOf`, since the constructor takes a lambda.
- **`FavoriteButton` owns the favourite→icon/tint mapping** (Task 13), in `features/shared/presentation/components/`. The same shape as sanctioned convention 2 and for the same reason: an assembler cannot return a `Painter` or a `Color`, and a screen must not branch on data. It is **not** in the design system, because nothing about "favourite" is a design concept — it is built *from* `AppIconButton`. It reports a *tap*, never a toggle: adding is immediate and removing opens a dialog, so the screen decides which a tap meant.
- **`cd_*` is the content-description prefix, and those strings are interpolated** (Task 13), closing Task 11's forward reference. `cd_add_favorite` / `cd_remove_favorite` name the character (`%1$s`) so a list does not announce twenty identical buttons. They are the app's **first** interpolated resources, which is why `CharacterUiStringsTest` exists in `iosTest`: Compose Resources substitutes only indexed placeholders and emits a bare `%s` literally *with no error*, and the `commonTest` mapper test compares resource **keys**, so it is structurally blind to a malformed placeholder. Any future interpolated string needs the same iOS-side check.
- **`AppTheme` must provide `shapes`, not just colours and typography** (Task 11). The ColorScheme comment already warns that an unmapped M3 slot is stock Material rather than a fallback; the same was true of shapes and went unnoticed — an `AlertDialog` rendered at M3's 28dp `CornerExtraLarge` while `AppRadius.md`'s own KDoc called 12dp the dialog radius. `ShapeTokens` now maps the M3 scale from `AppRadius`. **It does not cover buttons**: `ButtonDefaults.shape` reads a Material token directly rather than `MaterialTheme.shapes`, so a button wanting an app radius must be passed one at the call site.
- **Dialogs are previewed through a `Content` twin, never directly** (Task 11). A `Dialog` renders into its own platform window and never appears in a `@Preview` — on iOS it shows nothing at all. `AppConfirmDialog` is a thin `Dialog { AppConfirmDialogContent(…) }` wrapper; the twin paints its own surface, which also keeps the radius on `AppRadius` instead of Material's.
- **Compose Multiplatform's material3 does not bundle Material icons** (Task 11). `Icons.Filled.*` does not resolve in `commonMain` — `material-icons-core` is deprecated upstream and not a transitive dependency. Every icon in this app is therefore an **XML vector in `composeResources/drawable/`** loaded with `painterResource`, which is also what the reference project does on this stack. Design-system components take a `Painter`, never an `ImageVector`.
- **The favourite button's `contentDescription` is data-dependent** — "Add to favourites" vs "Remove from favourites" — so per the compose skill it must arrive from the assembler as a `UiText`, not be a static string in the composable. No `cd_*` strings existed then; **Task 13 added them** — see the `cd_*` entry below.
- **Edge-to-edge is on, so every screen must consume window insets** (Task 11). `enableEdgeToEdge()` in `MainActivity` means content draws under the status and navigation bars by default — verified: the Task 11 gallery's first row rendered underneath the clock. Nothing in the design system handles this, deliberately; **Task 12's `Scaffold` owns it** and must pass its `innerPadding` down, with `AppEmptyState`/`AppErrorState`/`AppLoadingIndicator` filling the padded area rather than the window.
- **Previews cannot be seen from the CLI, so a UI task needs a harness** (Task 11). The task introduced hand-written vector path data with no way to check it short of an IDE. A throwaway `TempComponentGallery` swapped into `App()`, screenshotted in both themes, then deleted, is how it was verified — and it is worth repeating for any task whose output is only reachable through `@Preview`.
- **System-bar icon contrast must follow the app's theme, not the device's** (Task 10). `enableEdgeToEdge()` decides it once in `onCreate` from `resources.configuration.uiMode`, and the stored `ThemeMode` is free to disagree — pick Dark on a light phone and dark status-bar icons get painted over a dark background. `SystemBarAppearance(darkTheme)` is an `expect`/`actual` called *inside* `AppTheme` so it sees the resolved value; the iOS half is a documented no-op because UIKit derives it from the controller's interface style. **Its mismatch case cannot be exercised until Settings exists — verify it in Task 21** by choosing a theme opposite the device's.
- **`App()` renders nothing until the theme store answers** (Task 10). `observeThemeMode()` is a cold flow, so a non-null initial value would not prevent a flash: the first frame would always be `SYSTEM`, and a stored Dark on a light device would show the light theme first. Gating on the first emission shows the platform window instead, whose `windowBackground` is colour-matched per mode. Two consequences: the placeholder/`Scaffold` must use `AppTheme.colors.background` (not `Surface`'s default `surface`) or the cold start steps colour, and **a screenshot taken too early catches the window rather than the app** — allow ~8s after a `cmd uimode night` change, which recreates the activity.
- **Kotlin names starting with `init` get a `do` prefix in Swift** (Task 10). `initKoinIos()` is exported as `InitKoinKt.doInitKoinIos()` — the Kotlin/Native exporter renames anything beginning with `init` so it cannot collide with Objective-C's initialiser convention. Check the generated `Shared.framework/Headers/Shared.h` rather than guessing a Swift name; `swift_name(...)` in that header is the truth.
- **Neither host depends on Koin** (Task 10). `initKoin(context: Context)` is an `androidMain` overload, so `:androidApp` names no Koin type at all and iOS calls the zero-arg `initKoinIos()` (Kotlin default arguments are invisible to Objective-C). Starting Koin is shared because **iOS has no `Application` class** — there is no pre-UI platform hook on that side.
- **`KoinGraphTest` resolves every binding; `koin.get<T>()` *is* the assertion** (Task 10). A missing Koin definition is a *runtime* failure — the app builds, launches, and dies when a screen first injects — so the test turns that into a build failure. Wrapping `get()` in `isNotNull()` adds a check that can never fail.
  It stubs only the two **leaves** that genuinely need an Android `Context` (`DataStore<Preferences>` and the DAO). `coreDataStoreModule` itself loads fine, because Koin evaluates `androidContext()` inside the definition lambda — stubbing its data source and use cases as well had made the test assert against its own fixtures for the whole theme half of the graph. The DAO stub does bypass `coreDatabaseModule`, so that one binding is proven only by the device launch check.
  Tear down with `application.close()`, **not `stopKoin()`**: these graphs use `koinApplication { }`, which never registers in `GlobalContext`, so `stopKoin()` is a silent no-op that leaks an `HttpClient` per test and never fires the `onClose` releasing the DataStore file lock.
- **A local *failure* falls through to the API, not just a local miss** (Task 9). The Task 7 review left this open: `getFavorite` returns `Result.Error` for a corrupt row, and the question was whether the detail screen should then error out. It should not — the favourites table is an offline cache for *reading* a character, not the authority on whether it exists, so an unreadable row must not make a character unviewable while the API can serve it. `getCharacter` therefore has three branches (stored → local, absent → remote, unreadable → remote). When the device is offline *and* the row is corrupt, the network error wins, which is the more actionable of the two. A **bounded retry** guards the local read first, so the fall-through only ever handles a permanent failure — otherwise a `SQLITE_BUSY` from a concurrent favourite write is indistinguishable from a corrupt row and costs the offline guarantee for a readable one.
  Two consequences to keep in mind: **`DataError.Local` is no longer reachable through `getCharacter`** even though the interface still declares the wide `DataError` (kept wide for the next multi-source read — do not narrow it to `Network`, and do not add a `Local` branch to the detail assembler), and the fall-through is **silent**, so a permanently corrupt row means a network round trip on every open with nothing telling the user their offline copy is unreadable.
- **Reusable fakes live beside their interface** (Task 9). `FakeCharacterRemoteDataSource` and `FakeFavoriteCharacterLocalDataSource` are in `commonTest/core/domain/datasource/`, not nested in one test class, because every ViewModel test from Task 14 on needs them. Both count calls, which is what lets a test assert the network was *not* reached — asserting only the returned value would pass even if the repository hit the API and discarded the answer.
  They mirror the real sources rather than being permissive, because a forgiving fake green-lights broken code: an unregistered page fails with `NOT_FOUND` exactly as the API does (serving `Success(empty, hasMore = false)` would make a paging off-by-one *pass* and leave the plan's end-of-list obligation untestable), `observeFavoriteIds` applies the same `distinctUntilChanged` the real source does, and the read/write error switches are separate because the observe functions have no error channel and a toggle test needs "reads fine, write fails". Seed with `seed(vararg)`, newest last — assigning a list positionally inverts the order `observeFavorites` depends on.
- **DataStore conventions, which no skill supplies** (Task 8). **Preferences, not proto**: this is one enum behind one key, and a typed store would mean a schema plus a serializer for a single value. The key is `stringPreferencesKey("theme_mode")` — snake_case to match the file's own convention rather than Kotlin's, and **treated as schema**: renaming it silently resets every user's choice. The stored value is `ThemeMode.name`, read back with a defensive lookup rather than `valueOf`, so a renamed constant degrades to `SYSTEM` instead of crashing on first read. One file, `settings.preferences_pb`, for all future preferences.
- **DataStore permits exactly one instance per file per process, and enforces it by *throwing*** (Task 8). `OkioStorage` keeps an `activeFiles` set and fails with "There are multiple DataStores active for the same file". *An earlier revision of this file claimed a second instance silently returns defaults — that is wrong, and it talked the tests out of the only probe that matters.* The path **is** released when the store's scope is cancelled, so a genuine restart test is writable: write, cancel the first scope, join it, then open a second store at the same path. The hazard this creates is a second `startKoin` in one process — Koin does not cancel a scope captured in a definition, so the definitions own their scope and cancel it via `onClose`, or the new store throws on first access and `observeThemeMode`'s `catch` turns a hard misconfiguration into "the theme setting just doesn't work".
- **`createWithPath` needs `okio` on the classpath by name.** It arrives transitively via `datastore-core-okio` as an `api` dependency, so the declaration is redundant for compilation — but a type this code names directly is declared, not leaned on.
- **A `ReplaceFileCorruptionHandler` is mandatory, not defensive** (Task 8). The default is `NoOpCorruptionHandler`, which rethrows on every read *and* every write, forever — so one truncated `settings.preferences_pb` would mean the user could never change the theme again on that install. A *missing* file is not corruption (the serializer returns its default), so this costs nothing on first launch.
- **DataStore's write failures carry no SQLite wording** (Task 8). Writes go through okio, which surfaces `ENOSPC` as `strerror` text — "No space left on device" on both platforms. `asLocalError` matches that in addition to the two SQLite forms, or `DISK_FULL` would be unreachable for every preferences write.
- **`Dispatchers.IO` works in `commonMain` — it just needs its own import** (Task 7). It is an *extension property*: `public expect val Dispatchers.IO` in coroutines' `concurrentMain`, with `public actual val Dispatchers.IO get() = IO` on native. Writing `Dispatchers.IO` with only `import kotlinx.coroutines.Dispatchers` resolves to the `internal val IO` backing field and fails with "it is internal" — which looks exactly like the API being unavailable. **Add `import kotlinx.coroutines.IO`.** `concurrentMain` is a visible source set for this project's target set (jvm + both iOS), so no seam is needed. *An earlier revision of this file claimed the opposite and built a three-file `expect`/`actual` around it, which also parked blocking SQLite work on iOS's CPU-sized `Dispatchers.Default`. Deleted.*
- **Room preserves flow context downstream of the query** (Task 7). `setQueryCoroutineContext` moves only the query body; `InvalidationTracker.createFlow` adheres to flow-context preservation, so anything after it — the entity→domain `map`, with a JSON decode per row — runs in the *collector's* context, i.e. the main thread once a ViewModel does `stateIn(viewModelScope, …)`. Hence the explicit `flowOn(Dispatchers.IO)` before `catch`.
- **`Flow.catch` completes the flow after emitting its fallback** (Task 7). With `stateIn(…, Eagerly)` the upstream is subscribed once per `viewModelScope`, so one transient read failure would leave Favorites empty for the rest of the process — and `SPEC.md` gives that screen no refresh affordance. A bounded `retry` therefore comes *before* `catch` in both chains.
- **`DataError.Local.DISK_FULL` can only be recognised from an exception message** (Task 7). `androidx.sqlite.SQLiteException` exposes no result code — it is `expect class SQLiteException(message: String)` and nothing more — so the text is the only signal on either platform. `androidx.sqlite`'s `throwSQLiteException` builds `"Error code: $code, message: $msg"`, so a real `SQLITE_FULL` reads **`"Error code: 13, message: database or disk is full"`** on both platforms; `asLocalError()` matches on that, and the test uses the real format rather than invented text. Fragile by necessity, but reachable, and a miss degrades to `UNKNOWN`.
- **Storage tests split by what they can actually reach** (Task 7). `FavoriteCharacterDaoTest` lives in **`iosTest`** and runs against a real in-memory SQLite via `Room.inMemoryDatabaseBuilder` — it cannot run on the JVM host, because `sqlite-bundled.aar` ships only Android `.so`s. It owns everything that is really SQLite's behaviour: the `ORDER BY`, a missing row being `null`, deleting an absent row, upsert replacing. The fake-DAO test in `commonTest` owns only what the data source *adds* — the `flowOn`/`retry`/`catch`/`distinctUntilChanged` chain. **Asserting SQLite's behaviour against a fake only restates how the fake was written**, which is how two tautologies got in before being replaced.
- **`NO_INTERNET` needs a platform seam — no common Ktor type names the offline case** (Task 6). `UnresolvedAddressException` is thrown only by CIO/`ktor-network`: OkHttp raises `UnknownHostException`/`ConnectException`, and Darwin wraps every non-timeout failure in `DarwinHttpRequestException` carrying an `NSURLError` code. Before `Throwable.asNetworkErrorOrNull()` existed, airplane mode — the failure users hit most — reported `UNKNOWN` and `error_no_internet` was a dead string that no code path could reach. Tested per platform in `androidHostTest` and `iosTest`, because the exception types only exist there.
- **The three timeout types are siblings, not subtypes** (Task 6). `HttpRequestTimeoutException` (from the `HttpTimeout` plugin) extends `IOException`; `ConnectTimeoutException` extends `ConnectException`; `SocketTimeoutException` is its own thing. Catching only the last one reported every plugin timeout as `UNKNOWN`. The three `HttpTimeout` values are also **staggered on purpose** (connect 10s, socket 10s, request 20s) — equal values let the timers race, making the message the user sees non-deterministic.
- **`expectSuccess` must stay `false`** (Task 6), and is now set explicitly with a comment. With `true`, Ktor throws `ResponseException` (an `IllegalStateException`) for every non-2xx, which would collapse `responseToResult`'s whole status table into `UNKNOWN` **without a single test failing**.
- **No DTO field gets a default** (Task 6). All twelve keys are present on every character; `type` and an unknown origin's `url` arrive as `""`, which is a value, not an absent key. A default would not add robustness — it would convert a contract change into silent permanent data loss, since Task 7 persists whatever the mapper produced as the user's favourite (`image = ""` renders a blank avatar with no error). Only `info.next` is genuinely nullable. `ignoreUnknownKeys = true` is still right: additive API changes must not break the client.
- **`Logger.DEFAULT` is wrong on both platforms** (Task 6). On the JVM it routes through slf4j, which has no binding declared here and so discards every message; on iOS it `println`s unconditionally, release builds included. `HttpClientFactory` therefore takes `logLevel` and `logger` as parameters and defaults to `LogLevel.NONE`.
- **Ktor does not throw `SerializationException` for a malformed response** (Task 6). `ContentNegotiation` wraps the kotlinx failure in `JsonConvertException`, which extends `ContentConvertException` and is **not** a `SerializationException` — so a `catch (e: SerializationException)` alone reports every malformed body as `UNKNOWN`. `safeCall` therefore catches `ContentConvertException` as well, plus `IllegalArgumentException` for a mapper rejecting a value that deserialized fine (`Instant.parse` on a bad timestamp). Both are "the response did not match what we expected", i.e. `SERIALIZATION`. Two tests pin this.
- **`safeCall`'s block returns the finished `Result`, not an `HttpResponse`** — unlike the skill's version. That puts deserialization *and* DTO mapping inside the protected region, which is what lets a mapper throw become `SERIALIZATION` instead of escaping to the caller. `getResult(route, parameters, transform)` composes request → status → body → map inside it.
- **Events must use `Channel<UiEvent>(Channel.BUFFERED)` with `send`, never `trySend`** (Task 4). `ObserveAsEvents` stops collecting below `STARTED`, and under `navigation-compose` the lifecycle owner is the `NavBackStackEntry` on both platforms — so a covered destination's events *queue and fire on return*, which is the behaviour we want. `send` suspends until a collector resumes; `trySend` discards silently when nothing is collecting, turning that deferral into data loss.
- **Resource text can only be asserted on iOS.** `getString` needs no Compose runtime but resolves through `Resources.getSystem()` on the JVM, which an unmocked host test cannot provide. `ErrorStringsTest` therefore lives in `iosTest`. This costs nothing: assembler tests compare `UiText` *values*, never resolved strings, which is what the MVI skill prescribes anyway. **Do not try to read resource text from `androidHostTest`** — it needs Robolectric.
- **`error_not_found` is wrong for the list's paging call site.** It reads "We couldn't find what you were looking for", which is right for the detail screen's missing character but wrong twice over for a page 404: the user scrolled rather than searched, and `SPEC.md` ends paging on `info.next == null`, so a 404 there is a client bug or a race that **retry cannot fix**. Task 14/16 should treat `NOT_FOUND` on a page as end-of-list rather than offering a retry.
- **The `Error.toUiText()` dispatcher is deliberately not defined yet** (Task 4). The skill prescribes one dispatcher over the `Error` marker for *use cases that span domains*, and this app has none: every ViewModel receives a `DataError` from a data source or from `CharacterRepository`, so `DataError.toUiText()` covers every call site through Task 22. Adding it now would mean an unused public function whose only branch — the `else` — is unreachable, which is the same smell as the `DataError` constants trimmed above. **Add it the first time something returns `Result<T, Error>`.**
- **`DataError.toUiText()`'s `when` has no `else`, and that is load-bearing.** Verified in Task 4: adding a constant fails the build with *"'when' expression must be exhaustive"* at that call site, which is how a new error is forced to get a real message instead of silently becoming "something went wrong".
- **`.dataOrNull()` is deliberately not defined.** `Result` has exactly the four helpers the skill specifies. The skill set uses `dataOrNull()` in one example, but this app's only multi-state unwrap is Task 9's `getCharacter`, which has three outcomes worth naming (failure / absent / present) and reads better as an exhaustive `when` than as a null-collapse that silently discards which error occurred. Unwrap with `when`. *(Closes the open item that was listed in `CLAUDE.md`.)*

`CharacterRepository` exists **only** for `getCharacter(id)` — the one genuinely multi-source read (local row if present, else remote) that the detail screen needs. Everything else talks to a data source directly, because `CLAUDE.md` reserves the word "repository" for multi-source coordination.

Favorites persist every value the API returns. The `episode` url list is stored as a single JSON string column, serialized in the entity mapper — no `TypeConverter`.

## Four sanctioned conventions

These are deliberate and already reviewed. **A review agent must not flag them.**

1. **Stateful errors are mapped by the assembler.** `CLAUDE.md`'s "error → `UiText` at emission" rule applies to *events*. A retryable error that is part of rendered state is held as `DataError?` in `ViewModelState` and mapped by the assembler via `toUiText()` — which is pure and imports no Compose.
2. **`AppStatusDot(status: CharacterStatus)`** in `core/designsystem/components/` owns the status→color mapping. The assembler must not import Compose, and a screen must not branch on data — so the branch lives inside a design-system atom. This makes `core/designsystem` depend on `core/domain`, which is allowed: every layer may read `core/domain`.
3. **Bottom-bar visibility derives from the nav back stack**, not from a `UiState`. The navigation shell has no ViewModel and no assembler; it sits outside MVI.
4. **`App()` touches a use case directly** via `koinInject<ObserveThemeModeUseCase>()`. It is the composition root, not a screen — no screen state is involved. **Not to be copied into a screen.**
